# Active context

Romero is implemented as a Rust 2024 library and CLI. `romero [--verbose] [ROOT]` uses an explicit existing directory or the current directory, reads only optional `ROOT/romero.yaml`, applies defaults for omitted settings, rejects non-string and unsafe paths, validates DAT input, and then creates missing managed directories.

The dependency baseline uses the latest stable crate releases as of 2026-07-25 and Rust 1.97.1. Direct versions are `anstream` 1.0.0, `atomic-write-file` 0.3.0, `clap` 4.6.4, `quick-xml` 0.41.0, `rusqlite` 0.40.1, `serde` 1.0.229, `serde-saphyr` 0.0.29, `sha1` 0.11.0, and `zip` 8.6.0. There are no development dependencies. Prerelease-only `serde-saphyr` 1.0.0-rc.1 and `zip` 9.0.0-pre2 are intentionally excluded.

The repository includes a root-level `romero.yaml` example using the default `library`, `work`, and `dats` paths.

The root README is the user-facing contract for the CLI. In a personal, conversational voice, it traces Romero to the author's long-used but unfinished personal C++ ROM manager, then presents the Rust project as its fast, automatic, user-friendly CLI successor for Redump-style collections. It uses the conventional user-facing term DAT without an implementation-format qualifier, documents Git-based Cargo installation while identifying prebuilt CI release binaries as future work, and makes clear that ZIP support is limited to DAT archives while compressed ROM sets are not currently supported. Its quick start consistently calls the managed directory `ROOT` and presents a repeatable workflow: optionally configure paths or create the defaults on first run, add DATs and work files, rerun after DAT or ROM additions, review incomplete output and work leftovers, and repeat. It also covers `romero [--verbose] [ROOT]`, the default directory layout, the optional three-key YAML configuration, newest-per-system DAT selection, automatically incremented work collision suffixes, the post-DAT cache-backed library/work hashing phase before content matching, the library-to-work-to-library reconciliation pipeline, CUE handling, `.miss` reports, and the conservative data-safety boundary. Its safety language distinguishes preserved ROM payloads from a successfully replaced work CUE and generated `.miss`/cache state.

The engine is split across:

- `config.rs`: pure configuration merge/path validation plus root and managed-path inspection through the production or in-memory filesystem adapter.
- `dat.rs`: filesystem-adapted direct Logiqx DAT and in-memory ZIP entry loading, catalog validation, and newest-catalog selection.
- `cache.rs`: rollback-journal SQLite with exclusive transaction locking and root-independent cache keys.
- `filesystem.rs`: the thin production OS adapter and the unit-test-only in-memory adapter with injected failures and operation counters.
- `cue.rs`, `reconcile.rs`, and `model.rs`: pure parsing, filename assignment, collision, multiset, and report logic.
- `engine.rs`: immutable DAT reverse indexes, the mutable indexed work inventory, one-pass library audit, content-only priority-queue matching, CUE FILE-count acceleration, immediate promotion/incomplete reporting, post-matching duplicate reporting, and summaries.

DAT header names retain their original spelling while catalogs are grouped and the newest catalog is selected. The streaming XML parser accumulates every header text fragment, including predefined entities such as `&amp;`, numeric character references, and CDATA, rather than treating each parser event as the whole field. Outer header whitespace is trimmed only after accumulation, preserving spaces around entity boundaries. Each selected header is then sanitized for its managed system name: control and Windows-forbidden filename characters become `_`, trailing periods/spaces are removed, and Windows-reserved names receive a leading `_`. Sanitized names drive library directories, `.miss` filenames, diagnostics, and cache-relative system paths. Collisions after case-insensitive sanitization fail before filesystem mutation. ROM filenames remain strict and unsanitized because DAT-exact promotion names are required.

The library is flat per selected DAT header. Only entries originating in library are quarantined to work, directories and non-regular work entries are ignored, and library-origin entries are never deleted. Games remain in library only when every expected filename independently matches size and SHA-1. Startup scans each tracked system once and retains only stable `GameId`s for verified complete games plus temporary cache-retention keys; it does not retain library file records.

Work is scanned once after the library audit, including files just evacuated from library. `WorkInventory` indexes regular files by relative path, basename, `(size, SHA-1)`, and sorted CUE keys. Every successful promotion, rewritten CUE, or library copy updates these indexes and the cache directly; there are no post-startup or final library/work scans.

Work matching uses content multisets and exact DAT filename assignment. There is no standalone CUE pass and a CUE cannot identify a game. Immediately after the `MatchingContent` event, every direct work CUE is read and parsed once. Valid documents are indexed in case-insensitive filename order by their number of `FILE` directives, counting repeated directives rather than distinct basenames or `TRACK` statements. Invalid CUEs remain in work and are excluded from alternate-CUE buckets; a read failure aborts before content matching mutates work.

Every non-CUE file participates in one fixed priority queue. Candidate games come only from exact `(size, SHA-1)` matches and must be incomplete when the queue is built. Lower candidate count wins priority, then case-insensitive work filename. Each queue seed evaluates every still-incomplete candidate using unprocessed work content first and DAT-derived paths from verified complete library games second. For a CUE game, an unprocessed exact expected CUE with matching size and SHA-1 is accepted regardless of its FILE count. An exact-name wrong-content CUE is the first rewrite candidate when valid and in the expected count bucket; remaining alternates come only from the bucket matching the game's number of non-CUE DAT entries. CUE rewrites preserve all non-filename bytes and line endings and are accepted only when the rewritten size and SHA-1 match the DAT. A complete candidate beats every incomplete candidate; complete ties use system/game order, while incomplete candidates use satisfied DAT entry count and then system/game order. A complete winner moves work sources and copies library sources directly to exact DAT filenames. An incomplete winner emits its diagnostic immediately and marks the seed, selected work content, displayed mismatches, and selected CUE processed.

After promotions finish, remaining work is checked against every complete library game in deterministic system/game order using work-only content multisets and the same CUE validation/rewriting rules as promotion. A full match emits one typed `DuplicateDetail` block with `OK` rows and reserves its selected physical files from other duplicate blocks, but it does not move, rewrite, or delete anything. Partial copies and CUE-only inputs do not qualify. Duplicate details are retained in `ExecutionSummary.duplicate_details`, included in `ProgressEvent::Duplicate`, visible at default CLI verbosity, and omitted from the final summary display.

The engine emits all typed `ProgressEvent` values through `run_with_progress`; CLI verbosity only filters rendering. `MatchingContent` is the sole matching-stage marker and renders as `Content matching` before the CUE index is built, so every immediate incomplete or duplicate block is visibly associated with content matching. `ProgressEvent::Incomplete` carries a public `LeftoverDetail`, `ProgressEvent::Duplicate` carries a public `DuplicateDetail`, and library-source progress uses `CopyingLibraryRom`. Default stderr includes phases, hashing paths without byte counts, game-level promotions, quarantine, library copies, immediate incomplete and duplicate blocks, ignored work entries, and reports. `--verbose` additionally renders hash saves, cache hits, successful periodic and final cache commits, promoted ROM moves, rewritten CUE writes, and rewritten CUE source removals. `CacheCommitReason` distinguishes `PeriodicCheckpoint` from `RunComplete`. The original `run` entry point remains quiet, and the final summary stays on stdout.

Immediate incomplete results use typed game-first diagnostics retained in `ExecutionSummary.leftover_details` for library consumers but omitted from `ExecutionSummary::Display`. Each selected system/game block contains every expected DAT ROM sorted case-insensitively by filename and labels it `OK`, `LIBRARY`, `MISSING`, or `MISMATCH`. Exact work matches print only the DAT filename, renamed work content prints `expected -> actual [OK]`, and content available from a verified complete library game prints `[LIBRARY]`. Work filenames are relative to the work directory and never include the configured work path. A mismatch means the exact DAT filename exists in work but its size or SHA-1 differs.

Content matching claims physical files only after choosing one winner. Claimed support and mismatch files cannot appear in a later winner. CUE alternatives prefer an exact expected basename with exact content, then an eligible rewrite of that exact-name sheet, then remaining same-FILE-count CUEs in case-insensitive order. Alternate references must resolve to selected work basenames or exact DAT names supplied from library. Unknown files are remaining non-CUE files with no DAT content candidate.

One shared ordering helper applies locale-independent Unicode lowercase comparison to every textual name/path sort, then uses original spelling as a deterministic tie-breaker. It covers DAT and ZIP discovery, production and in-memory directory scans, sequential processing, priority queues, filename assignment, promotion/removal ordering, library source choice, catalog/system/game selection, `.miss` files, and incomplete diagnostics. Non-text sorting such as hashes, dates, completeness state, and CUE byte ranges retains its natural ordering.

The CLI sends each incomplete and duplicate detail through `anstream` on stderr: interactive terminals receive bright cyan `Incomplete:` or `Duplicate:`, green `[OK]`, yellow `[LIBRARY]`, ANSI-256 orange `[MISMATCH]`, and red `[MISSING]`. Non-terminal stderr receives plain text, and standard `NO_COLOR`, `CLICOLOR`, and `CLICOLOR_FORCE` behavior is honored. The final stdout summary contains only totals and is independent of terminal color.

The fixed cache is `ROOT/.romero.sqlite3`. It stores managed area plus native relative path, size, nanosecond mtime, and SHA-1, so relocating the complete root preserves cache hits.

Every cache mutation uses one global fixed 60-second checkpoint scheduler: calculated hashes, path updates, generated-file rows, removals, and retention cleanup all remain visible in the active transaction. The timer starts with the first mutation after a commit and is evaluated at safe points before later cache mutations. A due checkpoint commits and immediately begins a new exclusive transaction; no hash, filesystem operation, inventory phase, promotion loop, or cleanup step forces its own commit. Successful completion commits the remaining batch. `Hash saved:` is immediate but does not imply durability; verbose commit events identify periodic and final commits.

Failure or interruption rolls back only the current batch even if completed filesystem operations remain. The next run hashes recent uncached files and repairs stale locations and deletion rows from the filesystem. The practical rollback window is about 60 seconds plus the operation in progress. Concurrent runs still fail immediately because each checkpoint begins another exclusive transaction.

Romero uses source-adjacent library unit tests only; Cargo integration-test auto-discovery is disabled and there is no `tests/` directory or binary test module. Tests use inline data, `MemoryFileSystem`, in-memory readers and ZIP cursors, injected clocks and failures, and SQLite `:memory:` with temporary storage forced to memory. They never invoke the CLI, access the filesystem or network, create temporary files, use external fixtures, mutate process-global state, sleep, launch subprocesses, or use containers. Thin production OS adapters remain untested where exercising them would violate these constraints. Operation counters verify that directory scans remain constant across promotions and that every work CUE is read once. Unit coverage includes configuration/path inspection and preparation, direct and ZIP DAT discovery, cache initialization and lifecycle, progress presentation, FILE-directive counting/indexing, CUE-only inputs, exact-name CUE precedence, same-count alternate selection, fixed queue ordering and ownership, filename-only rejection, complete-over-incomplete selection, complete-work duplicate reporting, cross-system/different-filename library sources, incomplete-source rejection, deterministic source choice, repeated missing hashes, logical root relocation, and newly promoted sources.

GitHub Actions provides non-mutating formatting, Clippy, and library-test checks for `main` and pull requests. Version tags matching `vX.Y.Z` and the Cargo package version build six single-binary ZIP archives for 32-bit and 64-bit Windows, static musl Linux, Intel macOS, and Apple Silicon macOS, then create or update a generated-notes GitHub Release only after every build succeeds. Workflow concurrency cancels superseded runs for the same Git ref, and release publication is safe to retry by replacing existing assets.
